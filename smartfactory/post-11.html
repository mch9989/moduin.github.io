제조 기업의 스마트팩토리 구축에서 가장 빈번하게 발생하는 분쟁 지점은 경영 관리 영역인 ERP(전사적자원관리)와 현장 실행 영역인 MES(제조실행시스템) 사이의 경계면입니다. 평일에는 아무 문제가 없는 것처럼 보이다가도, 월말 재고 실사나 원가 마감 시점이 되면 "MES에는 생산 완료가 찍혔는데 ERP 창고 재고에는 안 잡혔다"거나 "동일한 자재 투입 실적이 두 번 차감되었다"는 사고가 터집니다.

1. 월말 마감 때마다 ERP 재고와 MES 현물 수량이 틀어지는 이유

데이터 불일치의 핵심 원인은 두 시스템의 트랜잭션 성격이 근본적으로 다르기 때문입니다. MES는 현장의 설비 가동과 작업자 바코드 스캔에 맞춰 초단위로 수천 건의 미세 트랜잭션을 쏟아내는 반면, ERP는 회계·수불 무결성을 검증하기 위해 무거운 비즈니스 로직과 잠금(Lock)을 동반합니다.

대표적 장애 사례: 현장 작업자가 실적 등록 버튼을 누르는 순간 ERP 서버의 응답이 지연되어 타임아웃(Timeout)이 발생했습니다. MES 화면에는 '전송 실패'가 떴지만, 실제로는 ERP 내부에서 뒤늦게 커밋이 완료된 상태입니다. 작업자가 실패 메시지를 보고 버튼을 한 번 더 누르면서 중복 수불이 발생합니다.

2. 동기식 직접 호출(Direct Call)의 한계와 스테이징 테이블 구조

현장 POP 단말기에서 ERP의 REST API나 RFC(SAP 등)를 동기식(Synchronous)으로 직접 호출하는 구조는 실무에서 반드시 피해야 합니다. ERP 정기 점검이나 네트워크 순단이 곧바로 현장 라인 정지로 이어지기 때문입니다.

  • 인터페이스 전용 스테이징 DB(IF_DB) 격리: 양 시스템 사이에 독립된 중간 테이블(IF_WORK_ORDER, IF_PROD_RESULT)을 두고, MES는 자사 DB와 스테이징 테이블까지만 로컬 트랜잭션으로 커밋한 뒤 현장 작업자에게 즉시 완료 응답을 줍니다.
  • 상태 코드(Status Flag) 기반 비동기 워커: 백그라운드 데몬이 STATUS = 'N'(미전송) 건을 주기적으로 폴링하여 ERP로 전달하고, ERP의 정상 처리 확인(ACK)을 받은 건만 STATUS = 'Y'로 마킹합니다.

3. 멱등성(Idempotency) 보장 및 예외 재처리 프로세스

네트워크 재시도가 수십 번 반복되더라도 데이터가 중복 반영되지 않으려면 모든 인터페이스 전문에 고유 트랜잭션 키(IF_SEQ / UUID)를 부여해야 합니다.

  • 수신 측 중복 필터링: ERP 수신 모듈은 데이터를 수불 테이블에 반영하기 전, 수신 이력 테이블에서 해당 IF_SEQ의 기처리 여부를 먼저 조회하여 이미 처리된 키라면 로직을 건너뛰고 정상 응답 코드만 반환해야 합니다.
  • 에러 코드 분리 및 대시보드화: 단순 네트워크 단절(ERR_NET)은 워커가 3회까지 자동 재시도하고, 품목코드 미등록이나 가용 재고 부족 같은 마스터 불일치(ERR_BIZ)는 무한 루프를 막기 위해 즉시 STATUS = 'E'로 격리한 뒤 관리자가 마스터 보완 후 원클릭 재전송할 수 있는 화면을 제공해야 합니다.

4. 현업 표준 인터페이스 설계 체크리스트

구분 현업 표준 설계 규격
통신 방식 현장 실시간 UI와 완전 분리된 스테이징 테이블 기반 비동기 배치/워커 구조
식별자 규약 모든 전송 레코드에 발신 시스템 생성 고유 키(IF_ID) 및 발생 시각(EVENT_DT) 필수 포함
마스터 기준정보 품목, BOM, 공정 라우팅은 ERP를 단일 원천(SSOT)으로 삼아 단방향 동기화
일일 대사(Reconciliation) 매일 자정 전일자 전송 건수와 수신 건수, 수량 합계를 자동 비교하여 불일치 시 알림 발송

완벽한 네트워크나 365일 무정지 ERP 서버는 현실에 존재하지 않습니다. 훌륭한 제조 IT 아키텍처는 장애가 나지 않는 시스템이 아니라, ERP가 몇 시간 동안 멈춰 있어도 현장은 1초의 지연 없이 돌아가고 복구 즉시 단 한 건의 수불 오차 없이 동기화되는 복원력 있는 파이프라인을 갖추는 데 있습니다.
