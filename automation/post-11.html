[업무자동화] 침묵하는 자동화 봇을 막는 웹훅(Webhook) 기반 실시간 관제 및 자가 복구 설계

무인 자동화 시스템을 구축한 뒤 가장 아찔한 순간은 에러 팝업이 떴을 때가 아닙니다. 새벽 2시에 돌았어야 할 정산 배치가 서버 재부팅이나 네트워크 교착으로 아예 실행조차 되지 않았는데, 아무런 에러 로그도 남지 않아 담당자가 3일 뒤에야 데이터가 비어 있다는 사실을 발견하는 '조용한 실패(Silent Failure)'입니다.

1. 에러 알림보다 무서운 '조용한 실패(Silent Failure)'의 위험성

프로그램 내부의 try-catch 블록은 프로세스가 살아 있을 때만 작동합니다. OS 업데이트로 인한 강제 재시작, 작업 스케줄러 권한 만료, 프로세스 행(Hang) 상태에 빠지면 내부 예외 처리 코드는 단 한 줄도 실행되지 못합니다.

2. 데드맨 스위치(Dead Man's Switch) 기반 생존 신고 아키텍처

진정한 무인 관제는 "에러가 나면 알려줘"가 아니라 "정해진 시간에 완료 보고가 안 들어오면 장애로 간주하고 경보를 울려라"라는 역발상에서 출발합니다.

하트비트 체크(Heartbeat Check) 동작 원리:
배치 프로그램은 모든 작업을 정상 마친 직후 마지막 단계에서 외부 경량 헬스체크 URL로 완료 신호(HTTP GET/POST)를 쏩니다. 감시 서버는 매일 오전 06:10까지 해당 신호가 도착하지 않으면 배치 미실행으로 판정해 즉시 관리자 메신저로 긴급 알람을 발송합니다.

3. 등급별 웹훅 알림 라우팅과 피로도 제어(Throttling)

모든 로그를 메신저로 쏘면 하루에 수백 건의 알림이 쌓여 정작 치명적인 장애 메시지를 놓치게 됩니다. 심각도(Severity)에 따른 철저한 분리가 필요합니다.

  • INFO (일일 마감 요약): 매일 아침 지정된 시각에 1회만 발송 (총 처리 건수, 소요 시간, 스킵 건수 요약).
  • WARN (일시적 지연 및 자동 재시도): 파일 로그에만 기록하고 메신저 발송 제외.
  • CRITICAL (데이터 정합성 오류 및 프로세스 중단): 예외 스택 트레이스 상위 5줄과 실패 파라미터를 담아 즉시 발송하되, 동일 에러 키는 30분 내 중복 발송을 억제(Throttling)합니다.

4. 윈도우 서비스(Windows Service) 자가 복구 및 워치독 구성

복구 계층 실무 설정 기준
OS 서비스 복구 정책 윈도우 서비스 속성 [복구] 탭에서 첫째/둘째/후속 실패 시 모두 '서비스 다시 시작(1분 후)'으로 설정
독립 워치독(Watchdog) 본체 프로세스의 메모리 점유율이 임계치(예: 1.5GB)를 넘거나 응답이 5분간 없으면 강제 종료 후 재기동
Graceful Shutdown 종료 신호 수신 시 현재 처리 중인 단일 트랜잭션까지는 커밋 완료 후 안전하게 리소스 해제

관제와 자가 복구 체계를 갖춘 자동화 파이프라인은 엔지니어가 매일 아침 서버에 원격 접속해 로그 파일을 열어보는 수고를 완전히 없애줍니다.
